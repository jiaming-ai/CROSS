Get started with CROSS

Open-source visual SLAM for multi-session mapping, tracking and relocalization on robots. Install it with one script, pick the mode for your RGB-D, stereo or monocular camera, map a place once and relocalize every later session in it, across changes in lighting, weather, season and furniture.

  • Linux
  • NVIDIA GPU + CUDA
  • ~10 GB disk
  • MIT code · model licenses

What CROSS does

A robot that comes back to a place it has seen before should know where it is. CROSS is a visual SLAM system that builds a map from a camera stream, saves it, and relocalizes later sessions in it: a new session starts without knowing where it is, CROSS finds its place in the map, and from then on tracks the camera in the map's coordinates while it adds the places that are new.

  1. Session 1 Map The robot drives once. CROSS stores keyframes, their poses and how they connect.
  2. On disk Saved map map.pkl and map.pkl.store/: the graph and its keyframe images.
  3. Every later session Relocalize and extend Starts with no pose, joins the map, reports map-frame poses, adds new places.

The world changes between sessions: day turns to night, furniture moves, leaves fall, people walk by. CROSS is built for that:

  • Multi-hypothesis tracking. The pose is a mixture of Gaussians over SE(3), so competing explanations stay alive until the evidence separates them. A session joins the map only when its placement is supported consistently, so one look-alike view cannot teleport the robot.
  • Every match is checked. Loop closures pass chi-square consistency tests before pose-graph optimization (GTSAM) uses them.
  • Any camera. RGB-D, stereo or a single camera, with or without wheel odometry, a VIO or an IMU.

Install CROSS

CROSS needs Linux, an NVIDIA GPU with CUDA and about 10 GB of disk. One script does the rest: it creates a virtual environment in .venv (Python 3.11, via uv, which it fetches if missing), installs PyTorch, CROSS and GTSAM, and downloads the model weights.

Terminal
$ git clone https://github.com/jiaming-ai/CROSS.git
$ cd CROSS
$ bash install.sh --stereo          # RGB-D modes + the VGGT-Omega modes (the usual choice)
$ source .venv/bin/activate

bash install.sh --help lists every option. Check the installation with python -m pytest -q (a few minutes).

Tip. Run every command from the repository folder: the model paths (models/...) are relative to it. Some models (the XFeat / LightGlue matcher and the image-retrieval network) download on first use, so the first run needs internet; after that, export CROSS_HUB_OFFLINE=1 uses the cached copies.

Quick start: map once, relocalize later

The whole workflow on two recordings of the same office from OpenLORIS-Scene, a public dataset recorded by a wheeled robot with an RGB-D camera and wheel odometry. It uses rgbd_wheel, which every install includes.

  1. Get two sessions

    The benchmark's script downloads the office package of OpenLORIS-Scene (seven sessions, "package" format) from Hugging Face and unpacks it; then convert two sessions to CROSS's folder layout:

    Terminal
    $ uv pip install py7zr        # the script unpacks .7z archives with it
$ bash benchmark/datasets/download_openloris.sh data/openloris office1-1_7
$ python scripts/datasets/convert_openloris.py data/openloris/office1-1 data/posed/office1-1
$ python scripts/datasets/convert_openloris.py data/openloris/office1-2 data/posed/office1-2

  2. Session 1: build the map and save it

    Terminal
    $ python run.py data/posed/office1-1 --mode rgbd_wheel --save-map maps/office/map.pkl

    A Rerun window shows the keyframes, the odometry and the current hypotheses as the map grows (on a server, add --no-viz). The map is two things side by side: map.pkl (keyframe poses and edges) and the folder map.pkl.store/ (keyframe images and descriptors). Copy or move them together.

  3. Session 2: relocalize in the saved map

    Terminal
    $ python run.py data/posed/office1-2 --mode rgbd_wheel --load-map maps/office/map.pkl \
    --save-poses office1-2_poses.txt --save-map maps/office/map.pkl

    The session starts without knowing where it is. Once CROSS has placed it in the map, office1-2_poses.txt gets one line per frame in the map's coordinates, in the TUM format (time x y z qx qy qz qw); frames before the session joined the map are left out. Saving again stores the extended map, now covering both sessions.

  4. Score it (optional)

    Terminal
    $ python scripts/map_and_reloc_rgbd.py --map data/posed/office1-1 \
    --query data/posed/office1-2 --out outputs/office --mode rgbd_wheel

    With ground truth for both sessions, this runs both and splits the second into independent 100-frame trials that each start without a pose; a trial succeeds when its final pose is within 2 m of the truth. outputs/office/ then holds the map, map_meta.json (the map's ATE) and reloc_summary.json (success rate and errors).

Common options

Outdoors, add the outdoor settings: --config configs/overlays/outdoor.yaml.

Reusing a map

  • Relocalize with the mode family the map was built with. A stereo map also accepts mono_wheel, mono_basalt and mono_imu, with the map's left camera.
  • Another robot, lens or stereo rig can relocalize in a map and extend it, in the stereo and the single-camera VGGT-Omega modes; stereo_imu and mono_imu only with images of the map's size. PnP and the Depth Anything 3 back end refuse another camera, and the single-camera modes' learned scale with another camera is untested.
  • A map built with --fast needs --fast.

Sensor modes: RGB-D, stereo or one camera

A mode names your sensors and your source of odometry in one word. Each is one configuration file, configs/modes/<name>.yaml, selected with --mode <name>.

Under each mode: the install option it needs (base: bash install.sh alone). The Basalt modes read odom_vio.txt, the poses of Basalt's stereo-inertial VIO, which needs a stereo pair and an IMU; benchmark/datasets/prepare_vio.py writes it for the benchmark datasets.

How to read the names

stereo_ rgbd_ mono_
The cameras. Stereo and single-camera modes measure poses with one forward pass of VGGT-Omega over the current image and the retrieved keyframes (fine-tuned for CROSS), except mono_dpvo, which uses the Depth Anything 3 back end. rgbd_ modes match XFeat + LightGlue features and solve PnP on the depth; rgbd_ff_ runs VGGT-Omega on the color image, scaled by the depth.
_wheel
Odometry from the dataset (odom_left.txt): wheel encoders, an INS or a phone's ARKit, despite the name.
_basalt
Odometry from a file written by Basalt's stereo-inertial VIO (odom_vio.txt).
_imu
CROSS fuses the IMU with its own model passes; no separate odometry needed.
_vio _dpvo
CROSS runs DPVO visual odometry itself (_vio: scaled by the IMU).
Which to try first. A stereo camera with any odometry: stereo_wheel, with 93% relocalization success in the benchmark. An RGB-D camera with wheel odometry: rgbd_wheel needs no large model and no non-commercial weights; the VGGT-Omega modes cope better with large changes in lighting and viewpoint. On an RTX 4000 Ada, relocalization runs at about 39 frames per second in rgbd_wheel, 10.6 in stereo_basalt (20.7 with --fast).

Use your own data

run.py reads posed RGB-D folders, stereo folders, KITTI raw, TartanAir V2, Virtual KITTI 2, OpenLORIS and Record3D (.r3d) files, and detects the format from the folder. For your own recordings, write one of two plain folder layouts:

RGB-D or one camera
my_sequence/
├── calib.json       intrinsics K, image size, fps
├── rgb/             000000.png, 000001.png, … (or .jpg; read in name order)
├── depth/           optional: one depth image per frame
├── poses_left.txt   one camera pose per image
└── odom_left.txt    optional: the robot's odometry, same format
Stereo
my_sequence/
├── calib.json       as above, plus T_right_in_left
├── left/  right/    one image pair per frame, same names
├── depth/           optional
├── poses_left.txt   poses of the left camera
└── odom_left.txt    optional

File formats

calib.json
{"K": [[fx, 0, cx], [0, fy, cy], [0, 0, 1]], "width": 640, "height": 480, "fps": 10}; stereo adds "T_right_in_left", the 4×4 pose of the right camera in the left camera's frame.
images
Undistorted (pinhole). Both stereo cameras share K; stereo_dpvo and stereo_imu need rectified pairs.
depth/
16-bit PNG in millimeters or .npy in meters.
poses_left.txt
Camera-to-world poses, one 4×4 matrix per line as 16 numbers (row by row), OpenCV axes: x right, y down, z forward. This is the ground truth, used only to evaluate; without ground truth, write your odometry poses here too.
odom_left.txt
Same format; CROSS uses the steps between consecutive poses. Without it, the odometry is simulated from poses_left.txt (noise-free, or noisy with --snr). --odom-file NAME reads another file of the folder.
imu.txt imu.json
For *_imu and mono_vio: t wx wy wz ax ay az (rad/s, m/s²), and the IMU's pose in the camera frame with its noise.
gnss.txt
Optional GNSS fixes, to place the map on the Earth (Large maps).

Converters for public datasets are in scripts/datasets/ (OpenLORIS, TUM RGB-D) and benchmark/datasets/ (KITTI, ROVER, OpenLORIS stereo, NCLT). Two phones on a bar make a stereo rig too: scripts/rig/ calibrates it from the phones' own recordings. To run on a live robot, feed frames through the Python API.

Guide: using your own data

Configuration

A run's settings come from four layers, each overriding the one before:

  1. Mode fileconfigs/modes/<mode>.yaml, with shared pieces from configs/base/
  2. Fast overlaywith --fast: configs/overlays/fast/<mode>.yaml
  3. Your files--config a.yaml b.yaml, left to right
  4. Single values--set section.key=value
Terminal
$ python run.py my_sequence --mode stereo_wheel \
    --config configs/overlays/outdoor.yaml my_robot.yaml \
    --set mapping.loop_closure.confidence=0.9995

Your own file (my_robot.yaml here) holds only the keys it changes, nested as in the mode files. A key CROSS does not know is reported with a warning and ignored (--set stops with an error); check the spelling against cross/core/config.py.

Shipped overlays

overlay in configs/overlays/use it for
outdoor.yamloutdoor scenes (larger distances)
odometry_vio.yamlexternal odometry from a low-drift visual-inertial odometry (a phone's ARKit / ARCore, a Basalt-class VIO on the robot) in a *_wheel mode
strict_merge.yamllarge or repetitive buildings, where a wrong relocalization costs more than a late one
stereo_lowband.yamlremote sessions over a thin link: the left image only, at half the rate
geo_anchor.yamlwith GNSS: place the map on the Earth without moving it

Camera mounting. The default assumes a forward-looking camera on a ground robot. For a tilted camera set mapping.projection.estimate_vertical=true; for a down-looking one mapping.projection.vertical=z.

Python API

Run CROSS inside your own program: build a session for a mode, optionally load a map, feed frames, and read the pose in the map.

Python
import numpy as np
from cross.core.config import load_config
from cross.dataloader.auto import load_dataset
from cross.pipeline import mode_config_files, build_session
from cross.core.types import Camera
from cross.utils.lie_tensor import normalize_SE3

dataset = load_dataset("data/posed/office1-2")
camera = Camera(K=dataset.rgb_K, frame_width=dataset.rgb_width, frame_height=dataset.rgb_height)
config = load_config(*mode_config_files("rgbd", "external"))  # = configs/modes/rgbd_wheel.yaml
session = build_session("rgbd", "external", camera, config)
session.load_map("maps/office/map.pkl")  # optional: relocalize in a saved map

to_matrix = lambda pose: normalize_SE3(pose).matrix().detach().cpu().numpy()
# frame: dict with rgb, depth, delta_pose (odometry), timestamp, ...
for i, frame in enumerate(dataset.replay_data()):
    if i == 0:
        frame["delta_pose"] = None  # the first frame has no motion
    session.process(frame)
    if session.localized():
        pose, _, _ = session.belief(to_matrix)  # 4x4 camera pose in the map
session.save_map("maps/office/map.pkl")
session.release()

On a robot, replace the dataset with a loop over your own frames. CROSS is a plain Python library (there is no ROS node): each frame is a dictionary with:

rgb
the color image, H × W × 3, uint8
depth or rgb_right
as the mode needs: depth in meters, or the right image of the stereo pair
delta_pose
the odometry step: the camera's 4×4 motion since the previous frame
timestamp
seconds

The stereo modes also need the rig: build_session(..., T_right_in_left=...). The modes with a monocular frontend need its configuration: cross.pipeline.session_factory(args, camera, config) returns a function that builds sessions of any mode from the runners' parsed arguments (add_session_args / finish_session_args); call it to get a session, as run.py does.

More capabilities

Remote sessions and large maps are part of CROSS. Two optional packages build on a saved map: cross_world reconstructs it as 3D Gaussians, and cross_nav adds navigation on the same VGGT-Omega backbone.

Remote sessions on a GPU server

The model and the map run on a GPU server. The robot runs only its odometry and cross-edge, a small package without PyTorch that sends images when the server will use them; network delays hold back only the map corrections.

The live VIO is tested on x86-64 only (not on aarch64 boards such as a Jetson), the edge replays recorded stereo folders in real time (a live camera driver is not included), and the link is not encrypted: use a network you trust.

cross-edge README

Large maps and GNSS anchoring

Maps stay on disk and load keyframe images when they are used, and long pose-graph optimizations run in the background. Optional GNSS fixes anchor a map to latitude and longitude; a later session's fix and compass then narrow the search.

Reference: map files, GNSS and compass

3D world: Gaussian splatting

cross_world trains 3D Gaussians (gsplat) on a saved map's posed keyframes, with the sensor's depth or stereo matching, and exports them to a web viewer; after a loop closure it moves them with the map without retraining. Monocular maps have no depth source yet.

CROSS World guide

Navigation: BEV occupancy

cross_nav adds a head to the VGGT-Omega pass that predicts a bird's-eye-view occupancy grid around the camera, with BEV planners, a trajectory policy and a robot agent on top. Install it with bash install.sh --nav.

CROSS Nav README

Run the benchmark

benchmark/ holds a fixed evaluation protocol with three tracks: T1 mapping accuracy (ATE), T2 multi-session localization (recall) and T3 relocalization success, on KITTI, OpenLORIS-Scene, ROVER and SimChange, for CROSS and six baselines: ORB-SLAM3, RTAB-Map, MASt3R-SLAM, VGGT-SLAM 2.0, LingBot-Map and AMB3R-SLAM. The published results come from 9,198 runs on 4 datasets with 120 sessions.

T3: the share of 10 s trials that start with no pose in a map from another session and end within 2 m indoors or 5 m outdoors, averaged over OpenLORIS-Scene, ROVER and SimChange. RTAB-Map had the same inputs as CROSS. LingBot-Map runs on one camera without odometry and has no relocalization step, so its T2 and T3 numbers are upper bounds; with the stereo pair alone, CROSS reaches 88%. ROVER and SimChange odometry is simulated from ground truth plus noise. All results and caveats

Terminal
$ export BENCH_DATA=/path/to/benchmark_data BENCH_RESULTS=/path/to/runs
# once per dataset: download and convert
$ bash benchmark/datasets/download_openloris.sh /path/to/openloris
$ python benchmark/datasets/prepare_openloris.py /path/to/openloris $BENCH_DATA/openloris
# the job list; restrict with --setups rgbd stereo mono, --scenes office home, --tracks t1 t2t3
$ python benchmark/jobs.py --dataset openloris --systems cross_rgbd cross_stereo orbslam3 \
    > queue.txt
# run the jobs (or split the lines over workers / GPUs), then make the tables and the page
$ while read -r job; do python benchmark/run.py $job; done < queue.txt
$ python benchmark/collect.py $BENCH_RESULTS && python benchmark/make_tables.py \
    && python benchmark/build_site.py

The baselines are built separately (benchmark/README.md). Outdoor datasets add the outdoor overlay automatically; tuning per dataset is not allowed. To test a change in minutes, the development split runs a small subset with the same protocol.

Troubleshooting

problemwhat to do
no window opens / the run fails on a serveradd --no-viz
CUDA out of memoryclose other GPU programs; in stereo_basalt and stereo_dpvo, try --fast
the new session never joins the mapmake sure the session revisits places that are in the map, and that the robot moves: a standing robot does not join (placements are tested at new keyframes). Check the calibration (K, T_right_in_left). A map built with --fast must be used with --fast
No module named 'dpvo'the mode needs bash install.sh --mono
the released VGGT-Omega checkpoint does not downloadit is gated: request access at facebook/VGGT-Omega and log in (huggingface-cli login). The default fine-tuned checkpoint is public
a setting has no effectlook for a config: unknown key(s) warning; --set with an unknown key stops with an error
CROSS asks [y/N] before it startsthe configuration has a documented risk; read the warning, or pass --accept-config-risk
the first run fails without internetmodels download on first use; run once online, then export CROSS_HUB_OFFLINE=1
